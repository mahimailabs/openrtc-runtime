title: "Why OpenRTC"
description: "Run every LiveKit agent from one worker, and see what each call is doing. Your Agent code does not change."
---

## The problem

A livekit-agents worker has one session entrypoint. The moment you have more than one agent (a booking agent, a support agent, a demo), you either write the dispatch yourself inside that entrypoint, or run a worker per agent. Either way, the parts you need to operate it are also yours to build:

- which agent should take this call,
- changing an agent's code without restarting the calls on it,
- seeing which call is slowing the worker down,
- keeping one client from using up the worker another client shares,
- shipping a new version without cutting anyone off.

OpenRTC is those parts, packaged around the livekit-agents you already run.

## What you keep

Your agents stay standard `livekit.agents.Agent` subclasses. OpenRTC has no base class and does not wrap `@function_tool`, `RunContext`, `on_enter`, `on_exit`, or the `*_node` hooks. Provider objects (`openai.STT(...)`) and provider strings (`"openai/gpt-4o-mini-transcribe"`) are passed to `AgentSession` unchanged.

What you delete is the per-worker wiring: the `entrypoint`, the `AgentSession(...)` construction, and `cli.run_app`.

## What you get

| | What it does | Limits |
| --- | --- | --- |
| **One pool** | Register every agent class on one `AgentPool`. Each call is routed to one of them by job metadata, room metadata, or room-name prefix. | A metadata value naming an unknown agent raises. Routing never falls back silently. |
| **Hot reload** | `openrtc dev` swaps live calls to your edited agent on their next turn, conversation intact. A bad save keeps the old code running. | Coroutine mode only. `openrtc start` never reloads. |
| **`openrtc top`** | A live, htop-style table of every call in the worker: agent, tenant, memory share, CPU share, and whether it is blocking the others. | Same host. In coroutine mode memory is an equal share of one process; in process mode it is each call's own. |
| **Tenants** | Per-tenant providers and API keys, per-tenant and per-agent session caps, and a circuit breaker that confines a failing tenant. | Shared process, not a sandbox. The breaker needs coroutine mode. |
| **Deploys** | A `deployment_version` tag, `pool.begin_drain()`, and audit events around livekit's own drain. | No live call is moved. Calls finish on the old version. |

[How it works](/how-it-works/) covers each of these in detail.

## Quick start

```bash
pip install "openrtc[livekit,cli]"
```

Python 3.11 to 3.13. The `livekit` extra pulls `livekit-agents[openai,silero,turn-detector]>=1.5,<1.9`; `import openrtc` alone does not import livekit. Set `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` as for any LiveKit worker.

Put one agent per file in a directory:

```python
# agents/restaurant.py
from livekit.agents import Agent
from openrtc import agent_config


@agent_config(name="restaurant", greeting="Welcome to reservations.")
class RestaurantAgent(Agent):
    def __init__(self) -> None:
        super().__init__(instructions="You help callers book a table.")
```

Then run the directory:

```bash
openrtc dev ./agents \
  --default-stt openai/gpt-4o-mini-transcribe \
  --default-llm openai/gpt-4.1-mini \
  --default-tts openai/gpt-4o-mini-tts
```

A room named `restaurant-call-1` now reaches `RestaurantAgent`. Edit the file during a call and the next turn runs your change. In a second terminal, `openrtc top` shows the call.

Prefer Python to a directory? Register the classes yourself:

```python
from livekit.plugins import openai
from openrtc import AgentPool

from agents.restaurant import RestaurantAgent
from agents.support import SupportAgent

pool = AgentPool(
    default_stt=openai.STT(model="gpt-4o-mini-transcribe"),
    default_llm=openai.responses.LLM(model="gpt-4.1-mini"),
    default_tts=openai.TTS(model="gpt-4o-mini-tts"),
)
pool.add("restaurant", RestaurantAgent)
pool.add("support", SupportAgent, greeting="Support here. What broke?")
pool.run()
```

`python main.py dev` and `python main.py start` then behave as they would for a livekit-agents worker.

## What it is not

It is not a way to serve more calls from the same machine. Against livekit-agents 1.8.3 on the same two cores, OpenRTC's default mode used about 3x less memory per call and, on uvloop, about the same CPU. One worker is still one Python process, so CPU caps it at about one core. The [benchmark](/benchmark/) has the numbers, the method, and where the CPU goes. Run one worker per core, or use `isolation="process"` for CPU-bound agents.

<Note>
OpenRTC is early and has few users so far. The supported surface is `openrtc.__all__`, listed on [How it works](/how-it-works/#public-api). Everything else can change between releases. Bugs and questions go to [GitHub issues](https://github.com/mahimailabs/openrtc-runtime/issues).
</Note>
