---
title: "Benchmark"
description: "OpenRTC against stock livekit-agents 1.8.3 on the same two cores: memory, CPU, where the CPU goes, and what happens under overload."
---

OpenRTC's default mode runs every call in one process. On the hardware we measured, that uses about 3x less memory per call than stock livekit-agents, and, on uvloop (the default since this release), about the same CPU. It does not make one machine serve more calls than CPU allows.

## Head-to-head

The same agent, 8 calls, run five ways on the same two pinned cores. Each configuration ran twice, interleaved, so drift over time could not favour one of them. Every agent answered in every run, except livekit-agents' thread mode, where one of eight did not speak in both runs.

| Worker | CPU (of 200%), run 1 / run 2 | Memory per call |
| --- | ---: | ---: |
| livekit-agents, a process per call | 120 / 121 | ~65 MB |
| livekit-agents, every call in one process (thread mode) | 140 / 142 | ~28 MB |
| OpenRTC, asyncio loop | 141 / 139 | ~22 MB |
| OpenRTC, asyncio loop, introspection off | 137 / 142 | ~22 MB |
| **OpenRTC on uvloop (default)** | **127 / 117** | **~22 MB** |

All five idle at about 1.2 GB (1.45 GB for thread mode): the runtime, the models, and livekit's shared turn-detector process. Memory per call is peak minus idle, over 8 calls.

- **Memory:** livekit-agents 1.8 forks each call from a preloaded process, so a call costs tens of MB, not the gigabytes older write-ups quote. OpenRTC's calls share one process and cost about a third of that.
- **CPU:** running every call in one process costs about 20 points more CPU on asyncio, in livekit-agents' own thread mode as much as in OpenRTC. OpenRTC's own code is not the cost: turning introspection off changed nothing. On uvloop, OpenRTC is back to about process-per-call CPU. The two uvloop runs spread 10 points apart, so read it as parity, not a win.
- **So:** coroutine mode saves memory at about the same CPU. It still does not raise the calls a machine can serve: one worker is one Python process, so run one worker per core.

### Where the extra CPU goes

CPU seconds per thread over 40 s in the middle of the 8 calls, read from `/proc` and named with `py-spy dump`:

| Thread | A process per call | OpenRTC, asyncio | OpenRTC, uvloop |
| --- | ---: | ---: | ---: |
| Python event loop(s) | 16.8 s | 18.3 s | 16.5 s |
| Voice-detection threads | ~9.2 s | 7.7 s | 7.1 s |
| livekit's Rust runtime (`tokio-rt-worker`) | 4.5 s | 11.7 s | 8.0 s |
| WebRTC network thread | 1.9 s | 3.8 s | 3.9 s |
| OpenRTC's CPU sampler | none | 0.2 s | 0.2 s |
| **All threads** | **46 s** | **50 s** | **44 s** |

The Python event loop does about the same work whether calls are spread over 13 processes or share one. The difference is livekit's Rust runtime: it hands every audio frame and room event to Python, each hand-off needs the GIL, and with every room in one process two Rust threads keep waiting on one busy interpreter. A py-spy profile shows the same waits, in livekit's FFI `put`, the event-loop wake-up, onnx and numpy. uvloop holds the GIL for less time per pass, so the Rust threads wait less.

Some of the Rust runtime's extra work is livekit's FFI queue, which offers every event from Rust to every subscriber in the process: each call's room listener and each pending request sees every other call's events. With the counter in the harness (`BENCH_FFI_STATS=1`), deliveries grow with the square of the calls in one process:

| Calls in one process | FFI events/s | Queue deliveries/s |
| ---: | ---: | ---: |
| 1 | 45 | 111 |
| 2 | 102 | 475 |
| 4 | 262 | 2,415 |
| 8 | 748 | 15,400 |

Eight calls in eight processes would make about 890 deliveries a second. A prototype that routes audio-stream events only to their own stream (`BENCH_FFI_ROUTE=1`) removed a quarter of the deliveries and did not move CPU beyond run-to-run noise (122 / 131 against 128 / 128), so the fan-out is a real cost but not most of it. The rest is one interpreter and one GIL doing the work of many.

### One worker per core

The same 8 calls on the same two cores, against one OpenRTC worker (uvloop, introspection off). LiveKit split the calls 5 and 3 between two workers in every run.

| Workers on 2 cores | CPU (of 200%), run 1 / run 2 | Idle | Peak |
| --- | ---: | ---: | ---: |
| 1 worker | 127 / 121 | 1.2 GB | 1.38 GB |
| 2 workers, one pinned to each core | 99 / 88 | 2.3 GB | 2.58 GB |
| 2 workers, not pinned | 109 / 114 | 2.3 GB | 2.58 GB |

Two pinned workers used the least CPU of anything measured here, about a quarter less than one worker and less than a process per call (120 / 121), and every agent answered. The price is memory: each worker loads its own runtime and models, so the second one adds 1.1 GB before its first call. Choose it when CPU is what runs out; on a memory-tight machine, one worker with process mode's CPU is the better trade. Raw runs: `results/multi-worker.jsonl` in the harness.

## Under overload

Coroutine mode used to report load to LiveKit as `active / max_concurrent_sessions`, which ignores CPU. A saturated worker kept saying yes. It now also reports event-loop lag, with 60 ms counting as full load.

24 calls arriving one every 3 s, two cores, OpenRTC coroutine mode. "VAD warnings" counts Silero's "VAD inference is slower than realtime" log line, a direct sign of a starved event loop. At 100 ms the load generator hung, so whether the agents spoke was not recorded.

| Full load at | Accepted | Agent spoke | VAD warnings |
| --- | ---: | ---: | ---: |
| 100 ms lag | 16 of 24 | not measured | 980 |
| 60 ms lag (shipped) | 12 of 24 | 12/12 | 85 |

The worker now stops at the edge of what it can serve and leaves the remaining calls for other workers. Something has to provide those workers: an autoscaler, or more replicas than you think you need. LiveKit reads load every 2.5 s, so a burst faster than that lands before the signal can react.

## Method

| | |
| --- | --- |
| Machine | Linux cloud container. The worker pinned to 2 cores with `taskset`; the load generator on other cores. |
| LiveKit | a local livekit-server 1.13, real rooms, WebRTC audio in both directions |
| Pipeline | Silero VAD and the turn detector (real models); STT, LLM and TTS stand-ins with realistic latency, so no provider variance |
| Memory | PSS, not RSS. Forked processes share memory pages, and RSS counts each shared page once per process. |
| CPU | busy time of the two pinned cores, from `/proc/stat`; per thread, `utime + stime` from `/proc/<pid>/task` |
| Admission | head-to-head: every worker admits every call (load = active / 200), so only the execution model differs. Overload run: livekit's production threshold, 0.7. |

## What this does not cover

- **Real providers.** STT, LLM and TTS were stand-ins. Real network calls are async and should not change the CPU picture much, but we have not measured them.
- **More cores.** Two cores. We have not measured several coroutine workers against one stock worker on four or more cores.
- **Capacity on uvloop.** The 16-call runs that found OpenRTC answering 14 of 16 predate uvloop; they have not been rerun.
- **Long calls.** Each run lasted minutes. Memory growth over hours is unmeasured.
- **Your agent.** A tool that does synchronous work (a blocking HTTP client, a large parse) costs every other call in a coroutine worker. `openrtc top` shows it as `slow`.

Measure on your own hardware before you quote a calls-per-worker number.

### Reproduce the head-to-head

The harness is in [`benchmarks/headtohead/`](https://github.com/mahimailabs/openrtc-runtime/tree/main/benchmarks/headtohead), with the raw results this page quotes. It needs Linux with 4 cores.

```bash
cd benchmarks/headtohead
./fetch.sh && ./server.sh
./sweep.sh      # about 25 minutes
./threads.sh
python3 summarize.py
```

<Note>
The overload run (24 calls, the 60 ms lag threshold) used an earlier version of the same harness; its raw results are not committed.
</Note>
